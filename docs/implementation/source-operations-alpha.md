# Organisation durable des sources — alpha 0.31

## Utilisation

Dans Projet, la palette ou les actions d’une source (onglet, clic droit, explorateur), choisir **Renommer cette source**, **Déplacer cette source** ou **Supprimer cette source**. Le dialogue prépare un aperçu chemin/nom CPC/entrée ; une confirmation native applique les changements. Annuler ne modifie ni les fichiers ni le manifeste.

Renommer prend un nom CPC de 1–8 lettres ASCII, chiffres ou underscores. `MAIN` renommé `TITLE` devient `src/title.bas` et `TITLE.BAS` sur le DSK. Son identifiant reste `main`, donc l’entrée continue de le désigner et le modèle Monaco conserve brouillon, undo/redo et curseur. Déplacer reçoit un chemin relatif sous `src/`, dans un dossier déjà existant, et conserve le nom CPC. Les autres buffers ne sont pas enregistrés.

Supprimer retire le fichier et sa déclaration, et propose une source restante comme entrée. La dernière source ne peut pas être supprimée. Si le buffer visé est modifié, la confirmation propose Annuler, **Conserver le brouillon et supprimer** ou **Enregistrer puis supprimer**. Conserver archive le texte dans le journal et l’historique sans l’écrire dans le fichier BASIC. Enregistrer effectue d’abord une sauvegarde explicite par le journal existant, puis prépare la suppression. Si la seconde étape échoue avant préparation, la sauvegarde demandée reste effectuée et la source reste déclarée.

**Rétablir la dernière organisation**, dans le panneau Projet ou les commandes, remet fichiers et manifeste dans leur état précédent. Après une suppression avec copie du brouillon, l’onglet réapparaît modifié : disque et buffer restent distincts. Les autres brouillons restent ouverts. La restauration n’est disponible que si tout le manifeste et les sources correspondent encore à l’état après l’opération ; une sauvegarde, un import ou un changement externe peut la rendre périmée. Une fois rétablie, cette opération n’est plus proposée. L’historique source conserve les versions avant/après et le brouillon, avec sa rétention commune de 20 snapshots/64 Mio.

**Consulter le brouillon conservé** ouvre aussi la copie de la dernière organisation en lecture seule, à sélectionner/copier. Elle reste accessible après une sauvegarde qui rend le rétablissement périmé. Le record courant est remplacé par la prochaine organisation ; les copies plus anciennes restent dans l’historique selon sa rétention, et leur consultation pour une source désormais absente reste à compléter.

## Contrats et reprise

Le domaine `packages/workspace/src/source-operations.ts` valide une action humaine unique et produit un manifeste cohérent. `SourceOperationsPort` expose préparer/appliquer, dernière opération/restaurer et lecture de la copie archivée. Les DTO comprennent l’aperçu opaque, les métadonnées de source, le manifeste et les sources disque ; les roots et candidats complets restent détenus par main. Un plan est lié à la session et au snapshot exact ; les données sont revalidées après confirmation. La politique agent, ses outils et ses droits ne changent pas.

Le mécanisme de l’agent est extrait dans `WorkspaceJournal`, avec deux politiques strictes : journal agent historique inchangé, et `.microide/source-journal/current.json` pour les actions humaines. Voir [ADR 0038](../adr/0038-organisation-durable-des-sources.md). Chaque version du journal est validée : identité du projet, propriétés exactes, sources avant/après complètes, empreintes et base64 canonique, UTF-8 sans BOM/NUL. Une organisation humaine ne modifie pas le contenu disque des sources. Le brouillon optionnel désigne uniquement la source supprimée. Les sources humaines gardent les bornes de 1 Mio/fichier et 8 Mio/ensemble ; manifeste 1 Mio/version, journal 28 Mio, union de 128 entrées maximum. La politique agent garde ses 64 Kio/source et 256 Kio/ensemble, et refuse toujours le renommage.

Aperçu sans écriture ; journal pending publié avant les fichiers, puis historique, sources et manifeste ; marqueur committed seulement après contrôle final. La restauration d’une opération terminée republie d’abord pending et suit le même protocole. À la réouverture après interruption : Annuler, Terminer l’organisation ou Rétablir les sources précédentes. Les seules versions admises sont les octets avant/après ou les absences prévues. Toute version inconnue bloque la reprise avant modification ; record corrompu/futur et temporaires sont conservés. Le projet peut être déplacé entre interruption et reprise.

Le brouillon archivé est conservé dans l’historique lors des deux choix de récupération. Après « Rétablir » à la réouverture, consulter l’historique de la source pour remettre cette copie dans le buffer ; elle n’est pas chargée automatiquement. Après « Terminer », le bouton de dernière organisation peut rétablir la source et sa copie. Les autres copies de brouillons restent des données distinctes.

## Limites et suite

IDE-003/008/009 et lot 1 restent partiels. L’ajout humain existant et l’entrée indépendante ne sont pas encore journalisés par ce nouvel incrément. Création de dossiers, import/duplication de source, éditeur de fichiers ordinaires, restauration historique d’un projet entier et migrations restent ouverts. Pas de renommage sémantique des noms de fichiers contenus dans le BASIC, ni de nouveaux droits IA. L’indexation des renommages Git reste refusée par la tranche Git actuelle ; le lot 3 doit compléter ce parcours. Les copies de brouillons plus anciennes peuvent demander le rétablissement de leurs chemins avant reprise.

Pas de verrou interprocessus ni de transaction atomique de l’ensemble du dossier. Les contrôles répétés ne ferment pas la course entre dernier contrôle et rename/unlink. Les dossiers doivent être ordinaires ; les collisions de casse, liens et hardlinks sont refusés ; plus de 4 096 noms dans un dossier bloque la vérification de portabilité. Fsync et sync de dossier sont utilisés sur les plateformes compatibles ; panne électrique, volumes réseau et persistance après panne Windows/macOS restent non qualifiés. Une recette de SIGKILL/arrêt de processus ne prouve pas une panne électrique.
